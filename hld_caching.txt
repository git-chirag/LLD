Caching & Redis - HLD Interview Notes
1. Why Cache?

Cache is introduced when:

✅ Read-heavy workload
✅ Expensive database queries
✅ High DB CPU utilization
✅ Low latency requirements

Without cache:

Client
  |
App
  |
Database

Every request hits DB.

With cache:

Client
  |
App
  |
Redis
  |
Database

Most requests served from Redis.

Benefits:

Reduced DB load
Lower latency
Increased throughput
Better scalability

4. Cache Eviction Policies

Cache memory is limited.

Need eviction.

LRU (Least Recently Used)

Remove least recently accessed key.

A B C D

Access A

B becomes oldest

Most common.

LFU (Least Frequently Used)

Remove key with lowest usage count.

Good for:

Trending content
Frequently accessed products

Redis supports LFU.

TTL (Time To Live)

Expire key after fixed duration.

UserSession
TTL = 30 min

Very common.

FIFO

Remove oldest inserted item.

Simple but rarely used.

5. Caching Problems
A. Thundering Herd Problem
Scenario

Popular key expires.

Product: iPhone

10000 users request simultaneously.

Cache miss for everyone.

10000 requests
      |
Database

DB crashes.

Solutions
Request Coalescing

Only one request rebuilds cache.

Others wait.

Req1 -> DB

Req2 -> Wait
Req3 -> Wait
Req4 -> Wait
Cache Warming

Preload important keys.

Startup
 |
Populate Cache
Randomized TTL

Avoid mass expiration.

B. Cache Consistency

Cache and DB disagree.

Example:

DB = ₹100

Cache = ₹90
Solutions

TTL

Expire every 5 mins

Write Through

Explicit Invalidation

Update DB
Delete Cache Key

Very common interview answer.

C. Hot Keys

One key receives massive traffic.

Example:

IPL Score
Bitcoin Price

Single Redis node overloaded.

Solutions
Replicate Hot Key
score_1
score_2
score_3

Distribute reads.

Local Server Cache
App Cache

Avoid Redis entirely.

6. Redis Internals
Why is Redis Fast?
In Memory

No disk access.

Single Threaded

No lock contention.

No context switching.

No race conditions.

I/O Multiplexing

Uses:

epoll (Linux)

One thread handles thousands of connections.

Concept:

Wait for events
Process ready sockets

instead of:

One thread per connection
Atomic Operations

Commands execute sequentially.

Example:

INCR counter

is atomic.

No locks required.

7. Redis Persistence

Redis is primarily memory-based.

Persistence prevents data loss.

RDB (Redis Database)

Snapshot-based.

Memory
 |
Snapshot
 |
Disk

Example:

Every 5 minutes

Redis forks process.

Child writes snapshot.

Parent continues serving traffic.

Pros
Small files
Fast recovery
Cons
Recent writes may be lost
AOF (Append Only File)

Every write operation logged.

Example:

SET user 1
INCR counter
LPUSH queue x

stored in file.

Recovery:

Load Snapshot
Replay Operations
Pros
Better durability
Cons
Larger files
Production

Often:

RDB + AOF

together.

Amazon Interview Sound Bites
When would you introduce Redis?

"When the workload is read-heavy, latency-sensitive, or database throughput becomes a bottleneck."

Most common cache strategy?

"Cache-aside with Redis."

Biggest cache challenges?

"Cache consistency, thundering herd, and hot keys."

Why is Redis fast?

"In-memory storage, single-threaded execution model, I/O multiplexing using epoll, and lock-free atomic operations."

Most important Redis data structure?

"Strings for caching, Hashes for objects, Sorted Sets for leaderboards, Streams for messaging."
