Build a complete Python 3.11+ Vending Machine System using clean object-oriented design, SOLID principles, composition over inheritance, proper encapsulation, and design patterns.

This project is intended to serve as a reusable Low-Level Design (LLD) reference implementation for Amazon-style interviews.

Generate production-quality code, not a toy example.

====================================================
BUSINESS CONTEXT
================

The system models a physical vending machine.

Users can:

* insert money
* select product
* receive product
* receive change
* cancel transaction

Admin can:

* add products
* refill inventory
* refill cash inventory

====================================================
IMPORTANT DESIGN DECISIONS
==========================

1. Use State Pattern.

Machine states:

* IdleState
* HasMoneyState
* DispensingState

Do NOT create transaction states.

Reason:

The machine state already represents the transaction lifecycle.

Avoid duplicated state tracking such as:

TransactionStatus.ACTIVE
TransactionStatus.CANCELLED
TransactionStatus.SUCCESS

These introduce synchronization issues.

Transaction should be a simple data holder.

====================================================
FUNCTIONAL REQUIREMENTS
=======================

1. Insert Money

User can insert denominations.

Supported denominations:

1
2
5
10
20
50
100
200
500

Machine balance should update accordingly.

====================================================

2. Select Product

Products are selected using slot codes.

Examples:

A1
A2
B1
B2

User can only purchase one product per transaction.

====================================================

3. Dispense Product

After successful validation:

* decrease inventory
* return change
* reset transaction
* transition back to IdleState

====================================================

4. Cancel Transaction

User may cancel before dispensing.

Machine should:

* refund inserted money
* restore machine state
* clear current transaction

====================================================

5. Change Handling

Machine maintains cash inventory.

Machine must verify:

* exact change can be returned

before dispensing product.

If exact change cannot be returned:

* reject purchase
* allow user to cancel

====================================================

6. Inventory Refill

Admin can:

* refill product inventory
* refill cash inventory

====================================================
NON FUNCTIONAL REQUIREMENTS
===========================

* Thread safe inventory updates
* Extensible payment architecture
* Extensible change calculation
* Clean separation of concerns
* OOP focused
* Interview friendly

====================================================
DOMAIN MODEL
============

Product

Represents a sellable item.

Fields:

product_id
name
price

====================================================

Slot

Represents a physical vending machine slot.

Fields:

slot_code
product
quantity

Responsibilities:

has_stock()

dispense()

refill()

Slot owns inventory state.

Slot must contain its own threading.Lock.

====================================================

CashInventory

Tracks available denominations.

Fields:

denomination_count

Example:

{
100: 5,
50: 3,
20: 10
}

Responsibilities:

add_cash()

remove_cash()

calculate_change()

can_make_change()

CashInventory owns its own lock.

====================================================

Transaction

Represents current transaction.

IMPORTANT:

No transaction states.

Fields:

inserted_amount

inserted_denominations

selected_slot

Responsibilities:

add_money()

reset()

====================================================

VendingMachine

Aggregate root.

Fields:

slots

cash_inventory

current_transaction

current_state

Responsibilities:

insert_money()

select_product()

cancel_transaction()

purchase_product()

change_state()

====================================================
STATE PATTERN
=============

Create abstract base class:

MachineState

Methods:

insert_money()

select_product()

cancel()

====================================================

Concrete States

IdleState

HasMoneyState

DispensingState

====================================================

Behavior Examples

IdleState:

allow insert_money()

reject select_product()

reject cancel()

====================================================

HasMoneyState:

allow insert_money()

allow select_product()

allow cancel()

====================================================

DispensingState:

reject insert_money()

reject select_product()

reject cancel()

====================================================

State objects should encapsulate behavior.

Avoid large if-else chains inside VendingMachine.

====================================================
CHANGE CALCULATION
==================

Use ChangeStrategy.

Create:

ChangeStrategy (ABC)

GreedyChangeStrategy

Responsibilities:

calculate_change()

can_make_change()

====================================================

Use dependency injection.

Do NOT instantiate strategies inside business classes.

====================================================
FUTURE EXTENSIBILITY
====================

Design system so future payment methods can be added.

Create:

PaymentStrategy (ABC)

Future implementations:

CashPaymentStrategy
UPIPaymentStrategy
CardPaymentStrategy

IMPORTANT:

Only CashPaymentStrategy should be implemented now.

UPI/Card should be placeholders.

====================================================
CONCURRENCY
===========

Implement thread safety.

Slot owns lock because it owns quantity.

CashInventory owns lock because it owns denomination counts.

Document race conditions in comments.

Example:

Two users attempting to purchase last Coke simultaneously.
