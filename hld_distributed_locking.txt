Interview Sound Bite

If asked:

"How would you ensure only one service processes an order?"

A strong answer is:

"First I'd see if I can avoid distributed locking using idempotency keys, unique constraints, or partitioned processing. If true mutual exclusion is required across multiple servers, I'd use a distributed lock, commonly Redis SET NX EX with TTL, ensuring safe lock release using ownership tokens. For stronger guarantees and fault tolerance, I'd consider ZooKeeper or etcd-based coordination."

That answer sounds much more senior than immediately saying "I'll use Redis locks."

This is exactly the level of thinking that separates a mid-level engineer from a senior engineer.

A lot of candidates hear about distributed locks and think:

Shared resource → distributed lock.

In reality, experienced engineers try very hard to avoid distributed locks because they:

Reduce throughput
Introduce failure modes
Cause contention
Are difficult to get right

1. Idempotency Keys
Problem

Solution

Both requests carry:

Idempotency-Key: abc123

Backend:

If yes:

Return previous result.

No duplicate processing.

Decision Framework (Interview Gold)

When interviewer asks:

Multiple servers modifying same thing. What will you do?

Think in this order:

Can database uniqueness solve it?
UNIQUE

Use that.

Can idempotency solve it?

Repeated requests?

Use idempotency key.

Can partitioning solve it?

Route all updates for same entity to same consumer.

Can optimistic locking solve it?

Conflicts rare.

Use version field.

Can DB transaction solve it?
SELECT FOR UPDATE
Only then consider distributed lock.
Example Amazon Might Ask

Multiple users buying last item.

Bad answer:

Redis lock.

Better answer:

First I'd use a transactional update or optimistic locking at the database layer. If inventory updates are event-driven, I'd partition by product ID so only one consumer processes inventory events for a product. I'd consider distributed locking only if those approaches aren't sufficient.

That's the kind of answer that sounds like an SDE2 rather than someone who memorized Redis locks.
