System Design Interview Notes: Distributed Rate LimiterTarget Level: SDE2 / L5 (Amazon & Tier-1 Tech)1. Core Requirements ChecklistFunctional RequirementsAccurate Throttling: Limit requests based on an identifier (IP address, API Key, or User ID).Granular Tiers: Support multiple limits for the same user (e.g., 100 requests/minute AND 50,000 requests/day).Feedback Mechanism: Inform throttled clients using standard HTTP status codes (429 Too Many Requests) along with headers like Retry-After.Non-Functional Requirements (The SDE2 Core Focus)Ultra-Low Latency: The rate limiter sits on the critical path. Check overhead must be < 3-5ms.High Availability & Fault Tolerance: If the rate limiter cluster or caching tier fails, the system must fail-open (allow traffic) to protect availability, rather than causing a cascading outage.Scalability: Scale horizontally to support 100M+ active users and hundreds of thousands of requests per second (RPS).Memory Efficiency: Minimize bytes stored per user to optimize cluster costs (Amazon Frugality).2. Deep-Dive: Core Algorithms1. Token BucketMechanism: A bucket has a maximum capacity (C). It is continuously refilled with tokens at a constant rate (r tokens/second). Each incoming request consumes 1 token. If no tokens exist, the request is dropped.Pros: Highly burst-tolerant. Memory efficient (only stores last_updated_timestamp and current_token_count).Cons: A massive burst of saved-up tokens can shock downstream, write-heavy components if not carefully tuned.Best Used For: Standard public API gateways (e.g., AWS API Gateway), multi-tenant SaaS services.2. Leaky BucketMechanism: Requests enter a First-In-First-Out (FIFO) queue of fixed size. They are processed ("leak" out) at a rigid, uniform, continuous rate. If the queue is full, new requests are dropped immediately.Pros: Guarantees a perfectly flat, predictable traffic line downstream. Completely eliminates spikes.Cons: Destroys user responsiveness. Legitimate bursts suffer from immediate queue latency or artificial rejections. Storing actual request queues consumes more idle memory than tracking numbers.Best Used For: Webhook delivery engines, e-commerce checkout pipelines, data ingestion layers.3. Fixed Window CounterMechanism: Time is split into strict blocks (e.g., 12:00 to 12:01). A counter tracks requests within that window. It resets to 0 exactly at the boundary.Pros: Easiest to implement. Minimal memory usage (1 integer per user per window).Cons: The Boundary Burst Vulnerability. A user can exhaust their entire limit at the end of Window A and again at the start of Window B, effectively driving 2× the allowed limit within a tiny timeframe.Best Used For: Edge infrastructure or CDNs (CloudFront/WAF) to catch basic, brute-force volumetric attacks.4. Sliding Window LogMechanism: Keeps a sorted timestamp log for every single request made by a user. When a new request arrives, logs older than (Current Time - Window Size) are pruned. The remaining log count is checked against the limit.Pros: 100% mathematically exact rate limiting. No boundary vulnerabilities.Cons: Memory Nightmare. For high traffic, storing every raw timestamp object quickly exhausts RAM. Scaling to millions of users is economically unfeasible.Best Used For: High-security, low-volume APIs (e.g., banking/payment transfers, password reset endpoints).5. Sliding Window Counter (The Modern Standard)Mechanism: A hybrid estimation approach. It looks at the request count of the current window and the previous window. It calculates a weighted average based on how far along the current window is.\(\text{Estimated\ Requests}=(\text{Count}_{\text{prev}}\times \%\text{\ remaining\ in\ prev})+\text{Count}_{\text{curr}}\)Pros: Prevents boundary bursts without the heavy memory overhead of the Sliding Window Log.Cons: It provides an estimated count, though it is 99%+ accurate in real-world scenarios.Best Used For: High-volume, distributed applications where precision and memory cost must balance out.3. 4. Distributed Scale Challenges (Interview Killer Points)Challenge A: Concurrency & Race ConditionsThe Problem: In a distributed cluster, multiple application nodes handle traffic for the same user concurrently. If User A fires 3 rapid requests, 3 separate nodes will execute a "Read-Modify-Write" cycle against the cache simultaneously. All 3 read the same stale token/counter value, approve the traffic, and cause an inaccurate writeback.The SDE2 Answer: Never suggest distributed locking (ShedLock, Redlock) during a fast critical path check—it tanks latency. Instead, propose using Redis Lua Scripts. Because Redis processes Lua scripts atomically on a single thread, the "check-and-update" logic runs isolated without lock overhead.Challenge B: Memory Math & Frugality (Show the Numbers)Be prepared to write this on the whiteboard to justify your database sizing for 100 Million Active Users:Sliding Window Log Design: Storing 100 requests per user as 64-bit timestamps:\(100\text{\ requests}\times 8\text{\ bytes}=800\text{\ bytes/user}\)\(800\text{\ bytes}\times 100\text{M\ users}\approx \mathbf{80}\text{\ GB\ of\ pure\ RAM}\)Token Bucket Design: Storing a token integer and a timestamp:\(2\times 8\text{\ bytes}=16\text{\ bytes/user}\)\(16\text{\ bytes}\times 100\text{M\ users}\approx \mathbf{1.6}\text{\ GB\ of\ pure\ RAM}\)Conclusion: Token Bucket cuts cache memory requirements by 98%, lowering AWS operational infrastructure costs significantly.Challenge C: Multi-Region Synchronization vs. LatencyThe Problem: Global users route to different AWS regions (us-east-1, eu-west-1). If a user moves or shifts traffic across regions, how do regions keep up with their rate limit?The SDE2 Answer: Acknowledge the trade-off between Consistency and Latency. Synchronizing cache data globally via synchronous cross-region writes adds hundreds of milliseconds of latency, violating non-functional requirements.The Solution: Use Eventual Consistency. Allow local region cache clusters to handle immediate checks instantly. Sync token buckets across regions asynchronously (via Amazon DynamoDB Global Tables or background daemon syncs). Accept that a user might get temporary extra capacity during a sudden multi-region shift to protect system speed.5. Amazon Leadership Principle (LP) AlignmentDuring the discussion, subtly tie your engineering choices back to Amazon's principles:Customer Obsession: "I chose Token Bucket for the customer-facing Gateway because it supports bursts. If an e-commerce client loads a dashboard and fires 20 rapid asset queries, we shouldn't artificially lag their interface."Frugality: "By choosing Sliding Window Counter over Sliding Window Log, we reduce memory footprints from 80GB to 1.6GB, significantly cutting ElastiCache infrastructure overhead while maintaining strict system limits."Operational Excellence: "The rate limiter is configured to fail-open. If our Redis tier completely crashes, we log severe alarms but allow incoming user requests to pass directly to downstream services. It is better to risk backend stress than to guarantee an absolute outage for our users."To make sure you feel completely confident with this component for your loops, would you like to review the exact Redis Lua script implementation for a Token Bucket, or should we practice a mock interview scenario detailing how to build a rate limiter for an Amazon Flash Sale?
