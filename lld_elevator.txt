Build a complete Python 3.11+ Elevator System using clean object-oriented design, SOLID principles, composition over inheritance, dependency injection, and proper encapsulation.

This project should be production-quality and serve as a reusable Low-Level Design (LLD) reference for Amazon-style interviews.

====================================================
PROBLEM STATEMENT
=================

Design an elevator system for a building.

Users can:

* Press UP/DOWN button from a floor
* Enter an elevator
* Select destination floor

The system should:

* Assign hall requests to elevators
* Schedule elevator movement efficiently
* Handle multiple elevators
* Support future scheduling algorithms

Focus on scheduling and object-oriented design rather than UI simulation.

====================================================
DESIGN PHILOSOPHY
=================

Do NOT overengineer.

Avoid:

* FloorPanel
* ElevatorPanel
* Button
* Display
* Sensor
* DoorController

unless absolutely necessary.

This is an LLD project, not a hardware simulation.

====================================================
FUNCTIONAL REQUIREMENTS
=======================

1. Hall Requests

User can press:

* UP
* DOWN

from any floor.

Examples:

Floor 5 UP
Floor 10 DOWN

====================================================

2. Destination Requests

Passenger already inside an elevator.

Can select:

* Destination floor

Example:

Go to floor 17

====================================================

3. Elevator Assignment

System should choose the best elevator.

Factors:

* Current floor
* Current direction
* Pending requests
* Idle status

====================================================

4. Elevator Movement

Elevators should:

* Continue serving requests in current direction
* Reverse only after no more requests remain in that direction

Use SCAN (Elevator Algorithm) behavior.

====================================================

5. Capacity

Each elevator has:

* maximum capacity
* current load

Should reject requests if overloaded.

====================================================
NON FUNCTIONAL REQUIREMENTS
===========================

* Thread-safe request handling
* Extensible scheduling algorithms
* Clean object-oriented design
* Interview-friendly code
* High readability

====================================================

==========================

DESTINATION

====================================================

Do NOT use inheritance for requests.

Use:

@dataclass
class Request:
floor: int
request_type: RequestType

Reason:

Requests are primarily data containers.

Inheritance introduces unnecessary complexity.

====================================================
SCHEDULING STRATEGY
===================

Create:

ElevatorSchedulingStrategy (ABC)

Implement:

NearestElevatorStrategy

====================================================

Strategy must consider:

1. Elevator direction
2. Relative position
3. Idle elevators
4. Distance

Examples:

GOOD candidate:

Elevator at floor 3
Moving UP

Request:
Floor 5 UP

---

BAD candidate:

Elevator at floor 20
Moving UP

Request:
Floor 5 UP

Request lies behind elevator.

====================================================

Use a scoring mechanism.

Choose elevator with minimum score.

====================================================
REQUEST STORAGE
===============

ElevatorCar should maintain:

up_requests

down_requests

====================================================

Use:

Min Heap for UP requests

Max Heap for DOWN requests

====================================================

Example:

Current floor = 10

Requests:

15
18
4
2

Store:

up_heap:
15
18

down_heap:
4
2

====================================================

Elevator serves:

10 → 15 → 18

then

18 → 4 → 2

====================================================

This implements SCAN scheduling.

====================================================
CONCURRENCY
===========

ElevatorCar owns mutable request queues.

Each ElevatorCar should contain:

threading.Lock

Protect:

* request insertion
* request removal
* direction updates

Document race conditions.

Example:

Multiple hall requests arriving simultaneously.

====================================================
METHOD BEHAVIOR
===============

add_request()

Should:

* determine request direction relative to elevator
* place stop in appropriate heap

====================================================

move_to_next_stop()

Should:

* choose next floor
* update current floor
* update direction

====================================================

choose_next_direction()

Rules:

If current direction still has pending requests:
continue

Else:
reverse

Else:
become IDLE
